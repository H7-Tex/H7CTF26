# Reference solve

Twenty Questions is relative-graded: a correct recovery banks a floor, and the leaderboard rank is
gas efficiency (fewest debug events). "Solved" means the 16 recovered bytes match the run's flag;
the score is `0.25 + 0.75 * efficiency`, with `best_known = 285`.

Two reference programs, both assembled with `../challenge/interrogator/asm.py`:
- `baseline.tqa` : the correct but wasteful solve (breakpoint the confession, read every round). ~1807 gas, score ~0.58.
- `optimal.tqa` : the intended top solve (read the schedule tables, rewrite them to run only the 16 real rounds in order, read the plaintext straight from the register). ~285 gas, score 1.0. Generated by `gen_optimal.py`.

## Graded-path validation (what to run against a live instance)
`solve.py` assembles `optimal.tqa` and submits it to the portal, then prints the grader's JSON.

```
python3 solve.py <portal_host> <portal_port>
# expect: {"solved": true, "gas": 285, "score": 1.0, "flag": "H7CTF{...}", ...}
```

A pass = `solved: true`, `gas` at or near 285, `score` 1.0, and the flag string returned matches the
instance's dynamic flag. That exercises the full graded path: submit -> grader runs the program under
ptrace against the live sealer -> verifies the recovery -> reports the 0..1 score to the engine.

## Local validation (no platform, no grader)
The shipped `simulator` is the exact scorer binary. Run the committed sealer directly:

```
python3 ../challenge/interrogator/asm.py optimal.tqa /tmp/optimal.bin
TQ_MODE=live FLAG='H7CTF{test_flag_1234567}' \
  TQ_SEALER=../challenge/target/sealer TQ_WIN_BASE=0x4baac0 TQ_CONFESS=0x403019 TQ_BEST_KNOWN=285 \
  <the interrogator binary> < /tmp/optimal.bin
# -> {"solved":true,"gas":285,"score":1.0000,"flag":"H7CTF{test_flag_1234567}",...}
```

## Binary identity
The deployed image and the handout both use the pinned `challenge/target/sealer` (COPYed, not rebuilt),
so the addresses in `optimal.tqa` (`confess 0x403019`, `pre_loop 0x40301a`, window base `0x4baac0`)
match every instance. `sealer.c` is the source of record; rebuild and compare if auditing.

## Regenerating optimal.tqa
If the pinned binary ever changes, re-derive the addresses (`nm challenge/target/sealer`) and run
`python3 gen_optimal.py <pre_loop> <confess> optimal.tqa`, then re-pin the env in the Dockerfiles and
`services.yaml` to match.
